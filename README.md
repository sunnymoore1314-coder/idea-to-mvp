# Idea to MVP

把一个模糊、零散的产品想法，收敛成一套范围清晰、可直接进入开发阶段的 MVP 文档。

这个 Skill 不负责把想法变得更庞大。它的重点是理解真实问题、判断 AI 是否必要、主动控制第一版范围，并为后续开发固定关键决策和执行顺序。

当前版本：**2.0**

## 能做什么

- 从不完整描述中识别核心问题、目标用户和主要使用场景
- 判断 AI 在产品中是必要、实用、可选还是完全不需要
- 将原始想法改写为一句清晰的 MVP 定义
- 把第一版控制在一类用户、一个问题和一条主要流程内
- 区分核心功能、可选功能和明确不做的内容
- 评估范围风险以及产品、工程、AI 三类复杂度
- 生成相互一致的产品、决策、任务和构建上下文文档
- 在交付前检查范围、功能、任务和技术方案是否冲突
- 安全地创建、优化或续写已有 MVP 文档，不静默覆盖现有工作
- 用稳定 ID 追踪核心功能、成功标准、决策和开发任务

## 适用场景

适合以下类型的早期想法：

- 应用或网站
- AI 工具
- 自动化工具
- 内部软件
- 轻量 SaaS
- 尚未明确范围的软件产品

如果项目已经有完整需求、明确架构和可执行任务列表，通常不需要使用本 Skill。

## 运行模式

| 模式 | 使用条件 | 行为 |
| --- | --- | --- |
| `Create` | 当前目录没有 MVP 文档 | 从原始想法创建完整规划包 |
| `Refine` | 文档已存在，用户要求调整产品或范围 | 读取全部文件，保留已确认决策并同步修改受影响内容 |
| `Resume` | 部分文档缺失或规划尚未完成 | 保留已完成内容，只补齐缺口并重新验证 |

如果检测到已有文件，但无法判断用户希望优化还是重新创建，Skill 会先询问一次，不会直接覆盖。

## 生成结果

每次规划默认生成四个文件：

| 文件 | 用途 |
| --- | --- |
| `PRODUCT.md` | 定义用户、问题、核心流程、功能边界、技术栈和成功标准 |
| `DECISIONS.md` | 固定会影响后续实现的重要产品与技术决策 |
| `TASKS.md` | 将 MVP 拆成按依赖排序、可验证完成的开发任务 |
| `BUILD_PROMPT.md` | 为新的 AI 编码会话提供可直接继续开发的上下文 |

默认只生成规划文档，不会自动创建完整产品代码。

## 可追踪性

V2 使用稳定 ID 连接四份文档：

- `CF-01`：Core Feature
- `SC-01`：Success Criterion
- `D-01`：Product Decision
- `T-01`：Development Task

`TASKS.md` 中的覆盖矩阵会建立 `CF-* → T-* → SC-*` 关系。优化已有方案时保留仍然有效的 ID，避免任务状态和历史决策失去对应关系。

## 工作流程

```text
原始想法
  ↓
理解问题与目标用户
  ↓
判断 AI 是否必要
  ↓
整理 MVP 定义
  ↓
缩小第一版范围
  ↓
评估风险与复杂度
  ↓
生成四份开发文档
  ↓
检查并修正文档冲突
  ↓
交付可执行的 MVP 方案
```

## AI Role

Skill 不会默认给所有产品添加大模型，而是使用四级判断：

| 分类 | 含义 |
| --- | --- |
| `Essential` | 没有 AI 就无法成立核心体验 |
| `Useful` | AI 明显改善核心体验，但存在普通实现作为替代 |
| `Optional` | AI 是增强项，产品本身不依赖它 |
| `Unnecessary` | 普通规则或传统软件已经足够 |

AI 只应出现在真正需要理解、生成、归纳或处理非结构化信息的环节。

## 默认范围边界

除非属于产品核心，第一版通常不加入：

- 用户账号和复杂权限
- 支付或订阅
- 管理后台
- 社交系统
- 实时协作
- 多 Agent 工作流
- RAG 或向量数据库
- MCP 集成
- 微服务或 Kubernetes

推荐范围通常是：

- 一类主要用户
- 一个核心问题
- 一条主要用户流程
- 3–5 个核心功能
- 不超过三个主要页面
- 尽可能少的外部依赖

## 使用方式

将整个 `idea-to-mvp` 文件夹放入支持 Skill 的 AI 编码工具所使用的 skills 目录，然后提供一个早期产品想法，例如：

```text
我想做一个 AI 应用，帮我决定周末去哪玩。
```

或：

```text
我想做一个工具，告诉我一个东西值不值得买。
```

除非缺失信息会明显改变产品方向，否则 Skill 会使用合理假设继续完成规划，并将重要假设写入 `PRODUCT.md`。

## 示例

- [AI 周末规划助手](examples/weekend-planner.md)：展示一个低范围风险、单次结构化生成的轻量产品。
- [商品购买决策助手](examples/buying-assistant.md)：展示一个需要证据边界、但不依赖网页抓取或实时比价的分析工具。
- [费用平分工具](examples/expense-splitter.md)：展示普通规则已经足够、明确不应加入 AI 的产品。

两个示例用于验证相同流程能够适用于不同产品方向，而不会自动复制功能或架构。

## 一致性检查

交付前会检查：

- 是否只有一个主要目标用户和一个核心问题
- 核心流程是否明确
- 核心功能是否控制在合理数量
- 每个核心功能是否都有开发任务覆盖
- 任务是否错误包含明确不做的功能
- 产品文档与决策是否冲突
- AI 定位是否与实际功能一致
- 技术栈是否超过 MVP 所需复杂度
- 构建上下文是否能在新会话中独立使用
- 执行模式是否正确，是否避免静默覆盖已有文件
- `CF-*`、`SC-*`、`D-*` 和 `T-*` 是否唯一且完整关联

完整规则见 [validation-rules.md](references/validation-rules.md)。发现冲突时应先修正文档，再重新验证，而不是直接交付互相矛盾的方案。

## 设计原则

- 保留原始产品方向，不擅自替用户发明另一个产品
- 用合理假设减少不必要的反复提问
- 优先删除非核心范围，而不是增加基础设施
- 让每项任务都能执行并判断是否完成
- 让所有输出文件对同一个 MVP 保持一致
- 只有在用户明确要求开始开发时，才创建最小可运行项目骨架
